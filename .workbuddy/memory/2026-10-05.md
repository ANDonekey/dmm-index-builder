## 编写《方案-DMM预览视频解析与静态代理.md》

用户需求：番号 → DMM 预览视频直链；出站全走 sing-box 日本代理（可配置 socks5）；
直链签名固定永久保存（SQLite）；泛域名静态反代 `*.dmm.<domain>` → `*.dmm.co.jp`
（补 referer/origin、透传 Range、回 `immutable` 长缓存）对接 CF CDN 边缘缓存；
可选下载本地 / PicGo API / 自定义 HTTP 上传。

方案要点：
- 部署双形态：A=服务跑 VPS（代理走 localhost）；B=本机跑 + CF Tunnel（贴合"保存本地"）
- 域名规划用专属泛子域 `*.dmm.example.com`，别泛解析主域
- 推荐技术栈 Go（modernc.org/sqlite 纯 Go 免 CGO、x/net/proxy SOCKS5、ReverseProxy）
- CF Free 单缓存对象 512MB 上限 → 4k/4ks 大文件可能不缓存，只回源直传不影响播放
- PicGo 图床对 mp4 兼容性存疑，只适合小档位；大文件走 http provider（R2/Alist）兜底
- URL 优先级：upload_url > local_url > proxy_url > dmm_url（dmm_url 不给前端）
- 反代入站 host 白名单 `^[a-z0-9-]+\.dmm\.<domain>$`，sub 只拼 `.dmm.co.jp`，无 SSRF 面
- 负结果也入库，negative_ttl 7 天后自动重试；成功结果永不自动重解析，force=1 手动覆盖

## 用 2026-09-29 dump 实测验证「清晰度=URL 后缀」（已证实，且踩了一个大坑）

用户提示「清晰度只是地址中的后缀不同」——**实测证实成立**，已写进方案 §0.5 并产出 `probe-quality.py`。

数据（新版 dump）：
- source_dmm_trailer：1,797,870 行、**787,671 条 url 非空**（5 月版 773,515）
- 后缀分布：dmb_w 225,259 / mhb_w 188,772 / sm_s 44,520 / dmb_s 40,643 / hhb_w 1,029
- 两表交集 267,643 cid 中 **73,602 个后缀不同**（trailer=mhb_w vs sample=dmb_w）
  → **trailer 表档位普遍高一档，优先信 source_dmm_trailer**

已验证的结论：
1. 同 cid 两条记录**目录完全相同，只有文件名后缀不同**（…/jufe00225/jufe00225_mhb_w vs _dmb_w）
2. freepv 真实档位典型四档 `mhb > dmb > dm > sm`，**因片而异**（ssni00036 无 mhb）
3. **向上试档有效**：库里 hhb_w 那批 8/8 可用，最大 102,288,077 字节（≈1080p）
4. **freepv 天花板 = hhb**，4k/4ks 在 freepv 体系不存在（真 404），4K 只能走 /pv/ 签名链
5. **_w / _s 不能横向替换**（sm_s 可用 4/4，对应 sm_w 4/4 是错误页）——是两种不同资源
6. 库里少数条目是 `http://` 和 `cc3001.dmm.com`，**必须规范化成 https**（http 下 curl 取不到状态行）

### ⚠️⚠️ 本次踩的最大坑：代理隧道行污染状态码解析

**走 HTTP 代理时 curl -sI 输出最前面是 `HTTP/1.1 200 Connection Established`（CONNECT 隧道行），
真正的上游状态码在最后一个 `HTTP/` 行。** 我最初解析取第一行 → 所有 404 被误判成
"200 + 150 字节假 200" → 五档全判为不可用，结论差点完全反了。

正确响应长这样：
```
HTTP/1.1 200 Connection Established     ← 隧道
HTTP/1.1 404 Not Found                  ← 真的
Content-Length: 150
X-Cache: Error from cloudfront
```
判据：**bytes > 1024**（150 是 openresty 错误页 HTML）。Go 的 net/http 无此问题（自动处理 CONNECT），
手写 curl/脚本解析必须取**最后**一条状态行。

（trailer 表贡献 577,493，sample 268,613，升档覆盖 225,693 条）

### 性能关键（8 分钟 → 29 秒）
- **不要逐行扫全文件**：`source_dmm_trailer` 在偏移 12.4 亿 / 总 13.8 亿处。
  先扫 `COPY public.` 标记**按字节定位目标块**，只解析那两段。
- **增量刷写**：只写 dirty 集合（新增/升档的 cid）。每 5 万条全量重写 = O(n²/batch)，
  慢到十几分钟。
- URL 不落库：固定前缀 43 字符 × 62 万 ≈ 26MB 冗余，stem 还重复两遍
  → 分列存储 + `build_url()` 运行时拼，**82.4MB → 52.9MB**。

### ⚠️ verify-index.py 抓出的 4 个真实 bug（没有校验器会静默流到线上）
1. **stem ≠ cid 占 57.6%**（357,424/620,007）——目录名数字段去零规则不一致
   （104fsmd00029→104fsmd29 但 000_035→000_035）。stem 必须单独存列。
2. **破平/升档时只换 quality → 742 条混搭错误**：同一 cid 两表 stem 可能不同
   （118bst00013：trailer=118bst013，sample=118bst013r，**都是 dmb_w 同档**）
   → 必须整条替换 cdn+dirpath+stem+quality+variant；档位相同时 trailer 优先。
3. **CDN 主机不止 cc3001**：还有 `pv3001.dmm.co.jp`（多是 mhb 高档），
   只认 cc3001 会把 28 条 mhb 误降级成 dmb。cdn 字段化。
4. CRLF 行尾（`rstrip("\r\n")`，否则全表 0 条）、`\.` 块结束标记必须处理、
   `INSERT OR REPLACE`（`ON CONFLICT DO UPDATE` 配 WITHOUT ROWID 写不进去）。

## r18.dev 官方 dumps 接口实测（据此重写工作流）

页面：https://r18.dev/dumps

| 事实 | 值 |
|---|---|
| 更新频率 | **每周二 03:00~04:00 UTC**（不是每天！） |
| 格式 | .sql.gz，236~260 MiB 逐周增大 |
| 保留期 | **90 天后可能删除** → 回溯超 90 天会 404 |
| 许可 | **CC0** |
| 最新版 | `https://r18.dev/dumps/latest` |
| 实际后端 | **Wasabi S3**（eu-west-1），**307 跳转**到 r18dotdev_dump_<date>.sql.gz |
| Range | ✅ Accept-Ranges: bytes（支持断点续传） |
| ETag | "ed56035dabcb6cd447bb704e07143997-33" —— **带 -N 是分块上传 MD5，不能当整文件校验** |

**⚠️ 解析 latest 必须读 Location 响应头**（`curl -fsSI` + awk）：
`curl -L` 会把 307 跟随成 200，**测不出真实上游地址**。

工作流最终配置：`cron: '10 4 * * 2'`（周二 04:10 UTC，官方更新后留 10 分钟余量）——
**不要设成每天**，会重复处理同一份 dump 白耗额度。
`dump_date` 输入留空 = 跟随 latest；填日期 = 直接拼 S3 路径（实测 2026-09-22 → 200/259MiB）。
下载用 `curl -C -` 断点续传。产物 CDN 分布：cc3001 主导 + pv3001 少量。
